# 石湖诗社 · 投稿后台使用说明

面向两类人：**社员**（投稿、改稿）与 **社务**（审稿、上站、维护）。
后台用的是 [Decap CMS](https://decapcms.org)（原 Netlify CMS），本质是「浏览器里的表单 → 仓库里的 Markdown 文件」，本站仍是纯静态站，没有服务端数据库。

---

## 一、数据是怎么流动的

```
社员在 /admin/ 填表
      │
      ▼
docs/curated/poems/<短名>.md      ← Decap 生成的 Markdown（YAML frontmatter + 诗句正文）
docs/curated/members/<短名>.md
      │
      ▼  提交为 Pull Request（草稿 → 待审 → 发布）
社务审核合并到 master
      │
      ▼  运行 python scripts/build_curated.py
website/assets/js/*               ← 重建分片、检索索引、社员名录索引
      │
      ▼  运行 python scripts/verify_all.py 校验后部署
站点上线
```

关键点：**合并 PR 只是把稿子放进仓库，还要跑一次构建才会出现在站上。**

---

## 二、社员：怎么投稿

### 1. 进入后台

站内任意页面顶部 →「社员」→ 名录页上的 **社员投稿** 按钮，或直接访问 `/admin/`。
首次使用需用 GitHub 账号登录并授权。

### 2. 先建档案，再投作品

**作品的作者必须是已在册社员**，否则构建会报错。新社员第一次投稿的顺序是：

1. 打开「社员档案」→ 新建
2. 填 **档案短名**（英文小写，如 `shihuke`，此即文件名，建立后不要再改）
3. 填姓名、印章字（单字，显示在名录的红印里）、一句话小传等
4. 保存 → 提交审核

档案通过后，再去「社员作品」投稿。

### 3. 填写作品

| 字段 | 说明 |
| --- | --- |
| 篇目短名 | 英文小写，如 `shi-hu-chun-xiao`，作文件名。**上站后不要修改**（见下方「链接稳定性」） |
| 篇名 / 作者 / 体裁 | 作者从在册社员中选；体裁含旧体各式与「现代诗」 |
| 题解 | 写作缘起、背景，可留空 |
| 注释 | 词条 + 释义，逐条添加 |
| 赏析 | 正文按段落逐条添加，可署名 |
| 名句 | 句子 + 点评，可留空 |
| 出处溯源 | 如「选自《石湖诗社社课习作》（2024）」 |
| **诗句正文** | 一行一句；**空一行表示分段/分阕**（现代诗分节、词的上下阕都靠它） |

诗句正文示例（七绝，单段）：

```
湖光潋滟晓烟轻，
柳外莺啼一两声。
最是一年春好处，
石湖波上踏青行。
```

现代诗（两节，中间空行）：

```
湖水把天空折叠成一块蓝手帕
我坐在岸上，把影子交给风

远处有白鹭独自练习起飞
而我的句子，还停在水面发呆
```

### 4. 提交审核

保存后在「工作流」看板里把稿子从 **草稿** 拖到 **待审**。社务审核合并后即完成投稿。

## 三、社务：怎么审稿上站

1. **审稿**：在 `/admin/` 的工作流看板或 GitHub 的 PR 页面审阅，可直接在后台改稿后再合并。
2. **合并**：合并到 `master`。
3. **重建**：

   ```bash
   python scripts/build_curated.py    # 并入社库，重建分片与名录索引
   python scripts/verify_all.py       # 校验门，必须全绿
   ```

4. **部署**：把 `website/` 目录发布到静态托管即可。

### 构建脚本会做的事

- 读 `docs/curated/members/*.md` → 并入 `POETS_DATA`，slug 为 `member_poet_<短名>`
- 读 `docs/curated/poems/*.md` → 并入 `POEMS_DATA`，id 为 `member_<编号>`
- 只清理 `member_*` 命名空间，**不触碰** `open_`（全唐诗）与 `curated_`（古典补遗 66 首）
- 重算站点计数、重建全部分片、生成 `members-index.js`（社员名录页数据源）

### 链接稳定性（重要）

作品的数字编号记录在 `docs/curated/poem-ids.json`，由构建脚本自动维护：

- 新作品追加新号，**既有作品的号码永不变动** —— 已分享出去的链接不会失效
- 删稿后其号码作废、不回收
- 因此**篇目短名一经上站就不要再改**，改名等于换了一篇新作品（旧号作废、新号新建）

这个文件应随代码一起提交，不要手工编辑。

## 四、部署前必做的两件事

### 1. 填写真实仓库

`website/admin/config.yml`：

```yaml
backend:
  name: github
  repo: your-org/shihu-poetry   # ← 改成真实的 owner/name
  branch: master
```

### 2. 准备 OAuth 授权服务

Decap 的 GitHub 后端需要一个 OAuth 中转服务来完成登录，纯静态托管（如 GitHub Pages）本身不提供。三种常见做法：

| 方案 | 说明 |
| --- | --- |
| Netlify 托管 | 站点直接部署到 Netlify，用其内置的 Identity / Git Gateway，配置最省事 |
| Cloudflare Worker | 自建一个几十行的 OAuth 中转，托管在任意地方，成本最低 |
| 自建小服务 | 任何能跑 Node 的机器上跑官方 `decap-cms-github-oauth-provider` |

选定后在 `backend` 下增加 `base_url` / `auth_endpoint` 指向该服务。

## 五、本地模式（不连 GitHub，当前采用）

配置里已开 `local_backend: true`。在仓库根目录开两个终端：

```bash
npx decap-server                        # 终端 A：本地后端，直接读写 docs/curated/
python -m http.server 8080 -d website   # 终端 B：静态服务器
```

终端 A 出现 `Decap CMS Proxy Server listening on port 8081` 即就绪（首次运行要下载依赖，约一两分钟）。
浏览器打开 `http://localhost:8080/admin/`，无需登录即可填表，保存后直接写入本地 `docs/curated/`，不产生任何 PR。

写完重建看效果：

```bash
python scripts/build_curated.py
python scripts/verify_all.py
node scripts/verify_frontend.js
```

### ⚠️ 本地模式没有「工作流」看板

官方明确限制：**`editorial_workflow` 在本地模式下不受支持**。本地代理握手时只报告 `publish_modes: ["simple"]`，Decap 会自动降级为 simple 模式并在浏览器控制台打印一行提示。

这意味着在本地模式下：

- 后台**不会出现**第三节说的「工作流」看板，也没有草稿 / 待审 / 发布三段。
- 点保存 = 直接落盘到 `docs/curated/`，没有审核环节。

这不算问题——本地模式本来就是一个人（社务）在自己机器上操作，审核环节的意义在于**远程投稿**。等接入 GitHub 后端，`publish_mode: editorial_workflow` 会自动恢复生效，看板和 PR 审核流程一并回来。**配置无需改动。**

## 六、常见问题

**Q：投稿后为什么站上看不到？**
合并 PR 只是入库。要跑 `python scripts/build_curated.py` 重建并重新部署。

**Q：构建报「作者『XX』不在社员档案中」**
该作者还没有社员档案，或档案里的姓名与作品的作者字段不一致（注意空格与异体字）。先建/改档案。

**Q：构建报「id 与文件名不一致」**
有人手工改了文件名却没改 frontmatter 里的 `id`（或反之）。两者必须相同。

**Q：能上传图片吗？**
可以，媒体会存到 `website/assets/uploads/`。但当前诗作模板没有图片字段，如需配图要先扩展字段与渲染层。

**Q：字段不够用，想加一个**
必须两边同步：`website/admin/config.yml` 的字段定义 + `scripts/build_curated.py` 的解析逻辑（`parse_poem` / `parse_member`）。诗作记录是与《全唐诗》共用的 11 字段定长数组，新增内容一般应挂在既有字段下，不要随意加第 12 个字段。
